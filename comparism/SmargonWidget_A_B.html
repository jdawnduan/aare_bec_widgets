Verdict

What the data says

  • Same model, same spec, same env facts. B shipped a working widget in a third of the time and lines, with the reviewer that hunts bloat finding almost nothing to cut.
  • A shipped a more defensive widget: runtime device swap, failure reporting in the status label, Designer-editable presets, leak-checking conftest. The ponytail reviewer counts most of it as unrequested.
  • Both hit the same wall: the skill's test fixtures target a newer bec_widgets than the venv has. The skill-driven agent spent more tokens working around it than the plain agent.
  • The reviewers split exactly along their philosophies: the bloat hunter picks B, the BEC contract reviewer picks A. Reviewer 2 found no happy-path bug in either; its A-vs-B gap is persistence of presets, the container yaml line and test guards.
  • Reviewer 2's own port list (embed PositionerBox, synchronous mv, pairwise grid) walks A toward B's shape. The two verdicts converge on: B's structure, plus A's config persistence and input validation.

Suggested merge

  • Take smargon/b as the base: same working widget, a third of the code, built in a third of the time.
  • Port from A: the Dockerfile.rhel9 yaml line (both reviewers flagged it); the top-level-widget leak fixture; precision: 2 in the yaml.
  • Apply B's two ponytail cuts (drop the cleanup() override, flatten the row walker) if you agree with them.
  • Then take reviewer 2's fixes for B: validate before rebuilding in set_presets (and popup_error=True), store presets in a ConnectionConfig field with a SafeProperty(str) if saved layouts or Designer must carry them, fix the black line, extend USER_ACCESS instead of replacing it.
  • Add QMessageBox suppression and the leak check to tests/conftest.py (A's fallback shows the shape).

Method and caveats

Spec handed to both implementers (identical text) 
Build a BEC plugin widget in this repo (aare_bec_widgets) for the smargon goniometer omega rotation.
- Shows current omega angle of device `smargon_omega`, moves it.
- Preset moves: 0 deg (absolute), and relative +10, -10, +45, -45, +90, -90, +180, -180 deg.
- Presets must be easily configurable.
- Mock motion: `smargon_omega` is an ophyd_devices.SimPositioner. Add its yaml under
  aare_bec_widgets/device_configs/ (see demo_sample_camera.yaml for the pattern used by dev.sh).
- Widget must be discoverable by bec-app as a plugin widget (entry point bec.widgets.user_widgets
  -> aare_bec_widgets.bec_widgets.widgets already exists).
- Leave runnable tests. Run them headless. Commit on your branch when green.
Env: shared venv ../bec_widgets/.venv, PYTHONPATH=<worktree> on every call, no BEC services,
no files outside the worktree, no skill or workflow names in code or commits.
Protocol
  • Worktrees .worktrees/a (branch smargon/a) and .worktrees/b (smargon/b), both off main at 14f1f04. Your uncommitted WIP was not in them.
  • Fresh general-purpose agents, not forks, so neither saw the orchestrator's context. A was told to call bec-skills:bec-new-widget first and nothing else; B to call ponytail:ponytail first and never read the bec-skills plugin.
  • Reviewers were fresh agents told only "worktree a / worktree b". Reviewer 1 ran ponytail:ponytail-review on both diffs; reviewer 2 ran bec-skills:bec-focused-review inside each worktree with main..smargon/x. No prove, no post.
  • Screenshots: container aare-bec-widgets-rhel9, bec-app launched with -w and PYTHONPATH pointing at the worktree, yaml loaded with add_to_session, widget added and moved over RPC, grabWindow(0).
Caveats
  • n = 1. One run per arm, no variance estimate. Token and time numbers are the harness usage figures and include the skill's own reading.
  • CLAUDE.md is global and reached both agents, so "prefer the boring solution" was in A's context too. Only ponytail vs bec-new-widget differed.
  • Blinding is imperfect: B's code carries one # ponytail: marker comment (the skill mandates them), and the generated Designer files in both branches hint at tooling. Reviewers were not told what either means.
  • Reviewer bias is symmetric by design: the ponytail reviewer shares B's philosophy, the bec reviewer shares A's. Read each verdict with that in mind.
  • The smargon_omega device stayed in the container session between the two screenshots, so A's screenshot started from B's end position.

Decision by the orchestrating agent

Build widgets in this repo with your workflow (ponytail + CLAUDE.md). Gate each merge with bec-focused-review. Reach for bec-new-widget only for lifecycle-heavy widgets, and only after the venv moves to bec_widgets ≥ 3.38.

  • The spec was met by both, at a third of the cost in B. 243 vs 756 hand-written lines, 119k vs 217k tokens, 5.4 vs 17.4 minutes, both green and both moving the mock axis in bec-app. For a composition-shaped widget the skill's extra 500 lines bought runtime device swapping, a pydantic config and a leak-checking conftest, none of which the spec asked for.
  • The skill's value is the contract, and this repo already carries it. B inherited the contract by composing core PositionerBox and copying the layout of AareGridScanControl. Reviewer 2 confirmed B's lifecycle is clean with zero own subscriptions or threads. The skill re-derived that contract from scratch and re-implemented what PositionerBox already does.
  • The skill fought the environment. It assumes bec_widgets.tests.fixtures and _call_later (3.38+); the venv has 3.37.3. The 148-line fallback conftest and the thread-pool warm-up hack are the visible cost of that mismatch. Until the venv is upgraded the skill pays that tax on every widget.
  • Ponytail alone is not enough at merge time. Reviewer 2 found three things in B that matter on the beamline and that ponytail-review by design does not look for: the container entrypoint never loads the yaml, a bad preset list leaves partial state, presets do not persist in saved layouts. That review costs 27 minutes and 204k tokens, acceptable once per merge, not per iteration. Use ponytail-review during iteration (6 minutes) and bec-focused-review as the gate.
  • Where A wins. A widget that owns its own QTimer, QThread, SignalProxy or dispatcher subscriptions, or that must be Designer-editable and layout-persisted from day one. There the skill's checklist (cleanup contract, SafeProperty persistence, leak-checking fixtures) earns its lines. That is the case to use bec-new-widget, or at minimum bec-widget-safety-audit after a ponytail build.

default ponytail + CLAUDE.md

  • Compose core widgets (PositionerBox, DeviceComboBox, Image) before writing controls.
  • Copy the layout of an existing plugin widget; run bw-generate-cli and the repo's black/isort hook.
  • Keep one # ponytail: marker per deliberate shortcut; a reviewer reads it as intent.

gate bec-focused-review before merge

  • Catches BEC-contract gaps ponytail skips: persistence, container config, input validation, USER_ACCESS shape.
  • Use ponytail-review while iterating; it is 4x cheaper.
  • For widgets with timers or threads, add bec-widget-safety-audit.

switch bec-new-widget when

  • The widget owns timers, threads, proxies or its own dispatcher slots.
  • Designer editing or saved-layout persistence is a day-one requirement.
  • The venv is on bec_widgets ≥ 3.38, so the packaged fixtures exist and the fallback conftest is not needed.

Summary

  • One spec, two fresh agents, two worktrees. A used the bec-new-widget skill, B used ponytail + CLAUDE.md. Both delivered a working AareOmegaControl that moves a simulated smargon_omega through the preset buttons, verified live in bec-app on the RHEL9 container.
  • B was leaner on every measured axis: a third of the hand-written code, half the tokens, a third of the time, 4 tests instead of 19.
  • The blind reviewers split by philosophy. ponytail-review would cut 354 lines from A and 10 from B and picks B. bec-focused-review approves both with four fixes each and picks A for spec completeness and test guards.
  • The two reviews converge on one widget: B's structure (embed PositionerBox, synchronous scans.mv, +x/-x pairwise grid) plus A's preset persistence, input validation, the Dockerfile.rhel9 yaml line and conftest leak/popup guards.
  • Decision: build with your workflow, gate merges with bec-focused-review, reserve bec-new-widget for lifecycle-heavy widgets and for after the venv upgrade. Next concrete step: merge smargon/b with the ported items above; both branches stay in .worktrees/ until then.
  • Confidence: one run, one simple widget type, same model on both arms. The cost ratios are robust to that; the "A wins for lifecycle-heavy widgets" clause is an extrapolation, not a measurement.
